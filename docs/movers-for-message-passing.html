Verifying distributed protocols in Rust

Movers for Message Passing

How to prove a protocol built on channels by reasoning about one thread at a time — porting Civl's reduction, yield invariants, and refinement layers into Rust and Verus.

1A protocol, as an engineer would write it

Start with a messaging library. Channels are created, messages are sent without blocking, and messages are received by blocking until one arrives. Each receive endpoint belongs to exactly one thread. This is roughly what std::sync::mpsc or a small RPC runtime gives you.

Here is two-phase commit written on top of it. A coordinator asks each participant whether it can commit; if every answer is yes, it commits.

The property we want is unremarkable:

If the coordinator commits, then every participant voted yes.

Proving it directly is out of proportion to how obvious it is. The coordinator and every participant run concurrently, so the proof must characterize every state reachable under every interleaving. An inductive invariant has to describe, for an arbitrary point in the execution, which requests are in flight, which have been consumed, which replies exist but have not yet been read, and how those sets relate to the coordinator's loop counter. None of that appears in the programmer's own reasoning, which is closer to:

The coordinator asks each participant in turn — the order does not matter — and each participant answers with its own vote. When every answer is in, the coordinator decides.

Two things make that informal argument work. First, the coordinator treats send followed by recv as though it were an ordinary function call: nothing observable happens in between. Second, the order in which unrelated participants are asked does not matter. The methodology described here is a way to make both of those claims into checked proof obligations, so that the resulting proof looks like the informal argument rather than like a case analysis over interleavings.

The ingredients are Civl's: reduction based on Lipton's movers, yield invariants for the interference that reduction does not remove, and refinement layers for replacing a component by a coarser description of it. What follows is how each one is stated, and how it appears in Rust and Verus.

2Reading the code

The verified code is Rust, checked by Verus. Verus adds specifications and proofs to Rust and discharges them with an SMT solver. A reader who knows a program verifier but not Rust needs only the following.

A mathematical function, usable only in specifications. Erased before compilation.
proof fn
A lemma. Its requires/ensures are its statement; its body is its proof. Erased before compilation.

Executable code. This is what actually runs.

Pre- and postconditions.

For a parameter passed by mutable reference, its value before and after the call. Both appear in postconditions.
Ghost<T>
A value of type T that exists only in the proof and occupies no space at runtime. Written x@ to read the underlying value.
Tracked<T>
Like Ghost, but subject to Rust's ownership rules: it cannot be duplicated or discarded silently.
Seq, Set, Map
Mathematical sequences, sets and maps. Unbounded; specification-only.

Bulleted conjunction and disjunction, for readable multi-line formulas.

Projects the first field of an enum variant. Total: applying it to the wrong variant is well-typed and yields an unspecified value.
external_body
Marks a function whose body is not verified. Its specification is assumed. Every one of these is an axiom.

One Rust feature matters to the proof rather than to the syntax. Values have unique owners; a value that is not Clone cannot be duplicated. We give Receiver no Clone implementation, so a receive endpoint is owned by exactly one thread. Rust's type system then discharges the single-consumer condition that the proof needs, at no cost.

3The network is a history, not a buffer

The first decision is what the proof says about the network. The obvious choice — record the messages currently in flight on each channel — is the wrong one. That set both grows and shrinks, so every invariant mentioning it must be re-established after every send and every receive by any thread. Interference reasoning then appears everywhere.

Instead, record what has been sent, and derive what is in flight.

Both components only ever grow. The payoff is that an invariant of the shape every message ever sent satisfies P is stable under all interference for free: other threads can only append, and appending preserves a universally quantified statement about the existing elements. Facts of the form message m was sent on channel c are permanent, and can be carried across any number of interference points without being re-proved. In a message-passing proof, statements of that shape are most of what one writes.

What is in flight is then a derived notion, and it is the only place the channel discipline enters. A per-link FIFO channel delivers the message at the head; a bag channel delivers any message not yet consumed.

Both models share sent: Seq<M>. That is what makes the send history the right common representation: the bag model simply forgets the order when deriving what is deliverable. This also settles a question that would otherwise need care. Order in sent is observable only when a channel has a unique sender. Under per-link FIFO a channel is identified by a (source, destination) pair, so it has exactly one sender and concurrent appends cannot race. Under the bag model there may be many senders, but the semantics discards order, so the race is unobservable. Neither instantiation ever requires reasoning about concurrent appends.

4Which way do sends and receives move?

Reduction rests on Lipton's mover types. An action is a right mover if it commutes with any action of another thread that follows it, and a left mover if it commutes with any action of another thread that precedes it. A sequence of actions executed by one thread that has the shape

right movers· one non-mover· left movers

can be treated as a single atomic action: any interleaved execution can be permuted into one where the whole sequence runs uninterrupted.

For channels the assignment is forced, and it is the opposite of what one might first guess.

SEND-L

send is a left mover. Appending to a channel only ever enables other actions, never disables one. So send; x can always be rewritten x; send. The converse fails: send(m); recv(m) cannot become recv(m); send(m), because the message is not there yet.

In code: send is nonblocking, which is also the fourth of Civl's left-mover conditions. Its postcondition contains no environment step, so no interference point follows it.

RECV-R

recv is a right mover. Consuming a message only ever disables other actions, so it can always be delayed: recv; x can be rewritten x; recv.

In code: recv blocks, so it can never satisfy the non-blocking condition and can never be a left mover. Its postcondition therefore includes an environment step.

The consequence is the shape of a reduced block:

recv· local compute· send· send

which is exactly the shape of an event handler. A handler loop needs one interference point per iteration, at the receive, rather than one per channel operation.

Because both models present the same sent: Seq<M>, the commutativity obligations reduce to facts about sequences and multisets, proved once per channel model rather than once per protocol. 5Yield invariants, and what survives one

Reduction makes atomic blocks larger; it does not eliminate the points between them. At those points other threads run, and the proof needs to say what they may do. That is the role of a yield invariant: a named predicate that every thread may assume at an interference point and must preserve at each of its own steps.

Each thread carries a token describing its view of the network and the endpoints it owns.

Because Receiver is not Clone, a thread holding one knows no other thread consumes from that channel; because a per-link FIFO channel has a unique sender, its owner knows no other thread appends to it. Neither fact needs an argument — it is what the Rust type already guarantees.

A blocking receive is where a thread meets the environment, and its specification says so directly.

Read it as: the environment runs, reaching some state mid in which the invariant still holds; then a message deliverable in mid is consumed. The precondition P::inv(old(t).net) is this thread's share of the non-interference obligation.

send has no such existential — that absence is the reduction claim, and section 7 explains what has to be proved to earn it.

6Remote calls: the awkward shape

Return to the coordinator. Its inner two lines are

send request· recv reply

a left mover followed by a right mover — precisely the wrong order. Reduction alone will not merge them, and it should not: the server genuinely runs in between, so there is a real interference point inside every remote call. Yet the informal argument treats the call as atomic, and it is right to.

The gap is closed by Civl's abstraction step rather than by reduction. A blocking receive is not a left mover because it can block — but blocking is judged relative to the action's gate, the condition under which the action must not fail. Strengthen the gate to say a reply is already present, and the receive no longer blocks:

RECV-ABS

Replace recv by an abstraction whose gate asserts that the channel holds an unconsumed message. Under that gate it never blocks, so it satisfies the left-mover conditions, and send; recv becomes L · L, which reduces to one atomic action. The obligation has moved, not vanished: the caller must now discharge the gate.

In code: recv_abs, whose precondition is old(t).net.recvd(r.id@).len() < old(t).net.sent(r.id@).len() and whose postcondition contains no environment step.

What discharges the gate is ownership again. Each call mints a fresh reply channel and moves the reply capability into the request; the caller keeps the sole Receiver. Exactly one reply can be produced, and only this thread can consume it. Together with the handler being a left mover — so it commutes leftwards until it abuts the call — the reply provably exists by the time recv_abs runs.

7Commutativity is a property of the whole program

The claim that send is a left mover is not a fact about send alone. Mover types are relative to the pool of actions the program can execute. An action gated on channel c is empty would be disabled by an unrelated append, and then send would not be a left mover at all.

So a protocol must declare its complete set of actions, and prove that they interact as the reduction assumes. That declaration also carries the message type, the channel model, and the yield invariant, so that a thread's token fixes which protocol it is running:

A footprint is the set of channels an action may touch. The obligations are then:

FRAME

An action does not write outside its footprint.

lemma_frame: for every c not in the footprint, n1.chans[c] == n0.chans[c].

LOCAL

An action does not read outside its footprint either: an operation on an unrelated channel neither enables, disables, nor alters it. This is literally the statement that send is a left mover with respect to that action. Its second conclusion is Civl's left-mover conditions (1) and (2), gate preservation.

lemma_local_send and lemma_local_recv: from step(a, req, resp, n0, n1) and c outside the footprint, conclude step(a, req, resp, n0.do_send(c,m), n1.do_send(c,m)) and gate(a, req, n0.do_send(c,m)).

COMM

Actions with disjoint footprints commute. Stated existentially, as Civl does: every a; b execution can be reordered into a b; a execution reaching the same final state. A universal n_ab == n_ba would be false for nondeterministic actions, and abstract layers are nondeterministic by construction.

lemma_commutes, concluding exists|mid| step(b, .., n0, mid) && step(a, .., mid, n_ab).

NI

Every action preserves the yield invariant. This is the non-interference half of an Owicki–Gries proof, discharged once per action rather than once per pair of program points.

lemma_preserves_inv; and send additionally requires P::inv(old(t).net.do_send(s.id@, m)), which is the check at the thread's own step.

Why Ghost<ChanId> in the message

Msg::Prepare(Ghost<ChanId>) carries the identity of the call's reply channel. ChanId is a specification-only type, so it cannot appear in a running value; wrapping it in Ghost gives a variant whose payload is erased at compile time. It is the model's stand-in for moving a linear reply Sender into the request.

8A protocol that needs its invariant

Chang–Roberts elects a leader on a ring. Node i receives on the link from its predecessor and sends on the link to its successor. On receiving a value v: if v exceeds its own id it forwards v; if v equals its own id it declares itself leader; otherwise it drops the message. The property is that only the maximum id can ever declare itself leader.

Here the yield invariant does real work. Each message carries two ghost fields — its origin and how many hops it has travelled — which are erased at runtime and exist only for the proof. The invariant states that a message sitting on link j came from a real node, has travelled to j, and dominates every node it passed through:

The invariant quantifies over sent, the monotone component, which is why it survives interference without an argument. The leader case then closes in three steps: distinct ids force the returning message to have originated at this node; the hop arithmetic forces it to have made a full lap; and a full lap covers every node, so this node's id dominates all others. Each is a small lemma about modular arithmetic.

9Layers

The last ingredient replaces a component by a coarser description of it. In Civl a layer is an entire program with its own set of actions; layer k's atomic actions are layer k+1's primitives. So refinement relates two protocols, and their action sets differ — related by an abstraction map, which need not be injective, since collapsing a family of concrete actions into one abstract action is the point.

The direction of the gate condition is the one that surprises people: the abstract action must fail more often than the concrete one. Anywhere the abstraction is safe to use, the implementation is safe too — which is what lets a caller reason with the abstraction and still conclude something about the code.

Refinement composes, so stacks of layers do. For Chang–Roberts the abstract layer has its own action type, a weaker invariant — messages are well formed, but nothing is claimed about domination or hop counts — and a nondeterministic step that forgets which message is forwarded. A subtlety worth naming: the refinement statement is not about the state on entry to the function, but about the state after the interference point inside it. The postcondition says there exists a state n_pre, reached once the environment has run, from which the whole body is one atomic action. That is Civl's condition that along every path there is exactly one yield-to-yield fragment behaving like the refined action.

10What is assumed

Verus checks that the obligations above are discharged. It does not, and cannot, check the reduction theory that makes those obligations sufficient — there is no formal execution semantics inside the Rust program to state Lipton's theorem against. So the boundary has to be drawn explicitly.

AssumedWhy
send, recv, recv_abs, yield_point, oneshot The channel primitives. Their specifications define the model; the runtime is not verified.
absorb_handler The reduction rule itself: a left-moving handler whose request has been sent may be executed at the call site, because a left mover commutes leftwards until it abuts its caller. This is Civl's synchronized asynchronous call, stated once — not a claim about any protocol.
Pool completeness That a protocol's action type enumerates every action of the protocol. Nothing prevents a handler being declared elsewhere. Discharged by review.

Everything else is proved: the mover facts about each channel model, the framing, locality, commutativity and non-interference obligations for each protocol, the remote-call combinator, the refinement conditions, and the safety properties of both protocols. The current development discharges 53 such obligations with no admitted goals.

The assumptions can be reduced further. Building a shallow trace semantics as specification-level data and proving the reduction theorem about it would relocate the trust from reduction is sound — a theorem about all executions — to these five functions implement this transition relation, a much smaller and more reviewable claim. That is the natural next step, along with the inductive rule needed for protocols that gather quorums.
